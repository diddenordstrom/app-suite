# Deploying with Komodo

## Decision

- **[Komodo](https://komo.do) runs the app stack from `main`.**
  - A resource sync applies [deploy/komodo/app-suite.toml](../../deploy/komodo/app-suite.toml) on every push. It updates the stack's settings but never deploys it (`deploy = false`): it runs before CI has built the images, so a deploy from it pulled images that did not exist yet (2026-11-10, after the Fartlek/Kvitt rename).
  - The CI `deploy` job calls the stack's deploy webhook once the images are pushed, and it is the only trigger. The request is signed like a GitHub webhook.
  - Komodo pulls, writes `.env` from the stack's `environment` and runs compose.
- **Releases are automatic.** The repo is public, so GitHub Actions runs the full release flow (test, image, deploy) on every merge to `main`; nobody releases by hand in Komodo. Komodo only plays the watchtower: it pulls the new images and runs compose, and it holds the secrets.
- **Watchtower is gone.** Komodo's auto update, run daily by its Global Auto Update procedure, is the fallback for anything CI did not trigger.
- **Secrets are Komodo variables marked secret**, referenced as `[[NAME]]` in the TOML. The TOML is in git; the values are only in Komodo's database, which Komodo backs up nightly.
- **Routing:**
  - Cloudflare Tunnel sends `*.didrik.dev` and the apex to Traefik.
  - Traefik routes on `Host(...)` labels in [deploy/compose.yml](../../deploy/compose.yml).
  - Hostnames outside the stack (`sso`, `blog`) stay as explicit rules above the wildcard.
- **Two stacks:**
  - The apps, deployed by Komodo.
  - The infrastructure: Traefik and Komodo itself, in [deploy/komodo/compose.yaml](../../deploy/komodo/compose.yaml), started by hand once. Traefik lives there because Komodo's UI and webhook need it before Komodo can deploy anything.
- **Komodo is also the Docker UI.** No Portainer next to it: it would show the same containers and stacks twice and take memory on a small board.

The one-time steps and the "adding an app" recipe are in [deploy/README.md](../../deploy/README.md).

## Reasons

- Adding an app used to mean ssh to marvin, editing `compose.yml` and `.env`, `docker compose up`, and a new tunnel hostname. Now the hostname comes from a label and the compose file comes from git. The only manual step left is creating a secret's value in Komodo's UI.
- **SOPS + age (encrypted `.env` in git)** was the first idea. Komodo's own secret variables do the same job with nothing extra to install, and Komodo has no native SOPS step.
- **Proton Pass** has a CLI (beta) that injects `pass://` references. Its login goes through a browser, which suits a laptop better than a headless server.
- **Database: FerretDB on Postgres, not MongoDB.** Recent MongoDB needs CPU features some ARM boards lack. Komodo supports FerretDB.
- **One stack, not one per app.** It keeps today's `compose.yml` and project name, so Komodo takes over the running containers in place. Data stays where it was through `DATA_DIR` (Komodo variable `APP_SUITE_DATA_DIR`).

## Builds in Komodo as a second release path

Added 2026-11-11, when CI ran out of Actions minutes. [app-suite.toml](../../deploy/komodo/app-suite.toml) defines a Server builder on marvin, one build per app (root Dockerfile, `APP` build arg, pushed to ghcr.io with the same `latest` and commit tags as CI) and a procedure `release` that builds them one at a time and then deploys the stack. Builds have no webhook; only the procedure runs them. It skips CI's gates (tests, audit, image smoke test) and rebuilds every app, so CI stays the normal path and this is for when GitHub Actions can't run.

## Open

- Komodo's UI is on the internet behind its own login and 2FA. If that feels too exposed, put Cloudflare Access in front of `komodo.didrik.dev` with a bypass for `/listener/*`, which GitHub and CI need.
- Session secrets could be generated by each app on first start and kept in `/data`. That would leave only the Pocket ID client per app as a secret. Not done.
